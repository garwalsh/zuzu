How Band is used

Agent API · free plan

One identity per agent, not one bot with six prompts

Each role is a separately registered Band agent with its own API key, issued once at registration. Each opens its own WebSocket (band-sdk, Phoenix channels) and is a distinct participant in the room. An agent's id is what every audit entry is attributed to, which is why they are registered rather than simulated.

Band refuses to delete an agent that has execution history — correctly, since its id appears in trails that must stay resolvable. So names are namespaced (Zuzu-v2-Intake) and a deployment can be rebuilt without burning the good ones.

The mention is the routing

A Band message must carry at least one mention. That turned out to be the useful constraint rather than a nuisance: an agent decides who should act next by choosing who to address, and a message with no recipient would be an agent talking to nobody — which is what a log line is for.

The Auditor opens every room, because Band rejects a message whose only mention is its own sender, and because owning the record from before the first question happens to be true.

Band's own tool schemas, handed straight to the model

The agents reason with MiniMax-M3 through TokenRouter, which is OpenAI-compatible — so Band's tool definitions (band_send_message, band_get_participants, band_lookup_peers, band_add_participant) are passed to the model unchanged. It talks to the other agents in Band's vocabulary, not in a translation layer of ours.

A test pins that set against the SDK's own ALL_TOOL_NAMES. It was once populated from the REST service names instead, matched nothing, and failed completely silently.

Memory the agents own

three tiers, written mid-conversation

Semantic

Facts that outlive the call. The Extractor decides which answers are worth keeping and calls remember_fact. It chooses which; it never supplies the value, because the value came from what the applicant actually said.

Episodic

Calls that happened. The Auditor closes the file with record_episode, so a later call can refer to it rather than greeting the person as a stranger.

Procedural

Rules learned about this person — speaks Spanish, has no SSN, do not lead with it. learn_rule, also the Auditor. A guard rejects rules about Zuzu's own machinery, because those get read back to the applicant next call as something we remember about them.

Shared between agents, and between calls

Every agent that needs context calls recall_profile and gets the same three tiers — that is the sharing. It is not passed through the room, because relaying an applicant's date of birth through a language model is how a wrong value reaches a form.

Scoped by SHA-256(tenant ␟ caller), so the same person at two organisations is two files and the store never holds a raw phone number. A caller with no id gets no memory in either direction — every anonymous caller would otherwise hash to one shared key.

5

What we are not claiming

stated before you ask

Routing is emergent up to a point. An agent chooses who to address and does so over Band. When it declares its own part finished, the fixed role order picks who goes next rather than its choice.

Band's memory and hosted tools are not used. ff_memory and ff_create_tools are off on the free plan, so the three tiers are ours in Postgres.

The agents are asyncio tasks in one process, each with its own Band connection and key — not six deployments. One service, one deploy.
